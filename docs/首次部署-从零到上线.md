# 首次部署 · 从零到上线（Supabase + Vercel）

> **目标**：把 Silicon River 部署成一个能公开访问的站点。数据存 Supabase，前端和 API 都跑在 Vercel。
> **耗时**：首次约 40 分钟。按顺序做即可，中间有一步卡住就查第 7 节排查表。
> **前提**：本仓库已经做过一轮"可部署化"改造，改造清单见第 8 节。

---

## 0. 先看懂架构：四个部件各干什么

```
   你的电脑                Supabase                 Vercel（同一个项目、同一个域名）
 ┌──────────────┐      ┌───────────────┐      ┌────────────────────────────────┐
 │ Python 抓取   │ ───▶ │  PostgreSQL   │ ◀─── │ backend service                │
 │ 脚本（手动/   │  写入 │  6 张表        │  读取 │ FastAPI（Python 3.12）          │
 │ 定时任务）    │      │               │      │   /api/timeline 等 17 条路由     │
 └──────────────┘      └───────────────┘      ├────────────────────────────────┤
                                              │ frontend service               │
                    浏览器 ──────────────────▶│ React 18 + Vite + Three.js      │
                                              └────────────────────────────────┘
```

| 部件 | 跑在哪 | 干什么 | 为什么放这里 |
|---|---|---|---|
| 抓取脚本 | 你的电脑 | 从 Hugging Face 抓模型数据，写进数据库 | 定时任务，不需要常驻服务器；放本机零成本 |
| 数据库 | Supabase | 存 6 张表（模型 / 厂商 / 标签 / 分析 / 评分 / 同步日志） | 托管 PostgreSQL，免费层够用，公网可访问 |
| API | Vercel | 把数据库查出来变成 JSON | 与前端同一个 Vercel 项目，**同域部署** |
| 前端 | Vercel | 3D 螺旋时间轴界面 | 静态站点，Vercel 免费托管 |

### 全局最关键的一个设计

前端和后端在 Vercel 上是**同一个项目里的两个 service，共用一个域名**。

带来的结果：前端请求走相对路径 `/api/timeline`，**不需要配跨域，也不需要填后端地址**。这就是仓库根目录 `vercel.json` 里 `services` + `rewrites` 的作用。前端代码一行都会不改。

> 这也是为什么 `.env` 里的 `VITE_API_BASE` 要**留空**。填了反而会把请求指到错误的地方。

## 2. 第一步：建 Supabase 数据库

### 2.1 创建项目

1. 打开 <https://supabase.com> → 登录 → **New project**
2. 填写：
   - **Name**：`silicon-river`
   - **Database Password**：点 **Generate a password**，然后**立刻复制保存到密码管理器**。这个密码只在创建时显示一次，忘了只能重置。
   - **Region**：选 **Southeast Asia (Singapore)** 或 **Northeast Asia (Tokyo)**，离深圳最近，延迟最低。
3. 点 **Create new project**，等 1–2 分钟初始化完成。

### 2.2 复制连接串（本手册最关键的一步）

进入项目后：**Project Settings（齿轮图标）→ Database → Connection string → 选 `Session pooler` 标签页**。

你会看到类似这样一串：

```
postgresql://postgres.abcdefghijklmnop:[YOUR-PASSWORD]@aws-0-ap-southeast-1.pooler.supabase.com:5432/postgres
```

**要改两处**：

1. 把 `[YOUR-PASSWORD]` 换成 2.1 里那个真实密码
   - 密码里如果有 `@ : / ? # &` 这类字符，需要做 URL 编码（`@` → `%40`，`:` → `%3A`）
2. 末尾**追加** `?sslmode=require`

改完形如：

```
postgresql://postgres.abcdefghijklmnop:MyP%40ssw0rd@aws-0-ap-southeast-1.pooler.supabase.com:5432/postgres?sslmode=require
```

### 2.3 三个必须知道的坑

**坑一：一定要用 Session pooler，不要用 Direct connection。**

| 连接方式 | 主机:端口 | 免费层 IP 支持 |
|---|---|---|
| Direct connection | `db.项目ID.supabase.co:5432` | **仅 IPv6** ❌ |
| **Session pooler** | `aws-0-区域.pooler.supabase.com:5432` | **IPv4** ✅ |
| Transaction pooler | `aws-0-区域.pooler.supabase.com:6543` | IPv4 ✅ |

免费层的**直连只有 IPv6**，很多家庭宽带和公司网络连不上，会卡在"连接超时"。Session pooler 是 IPv4，哪都能连。

**坑二：用户名不是 `postgres`，是 `postgres.项目ID`。**

用共享连接池时必须带上项目 ID 后缀，否则认证失败。

**坑三：主机名里的 `aws-0` 里的数字不能自己猜。**

那是**池化器集群编号，不是区域名的一部分**。不同项目可能在不同编号上。**必须从面板复制**，不要手拼。

> **补充说明**：如果你后面换用 Transaction pooler（6543 端口），API 也能正常工作——代码里已经关闭了 psycopg 的自动预编译（事务模式不支持预编译语句）。但**本机跑抓取脚本时请用 Session pooler**，因为脚本是长连接，会话模式更合适。

## 3. 第二步：在本机把数据灌进去

### 3.1 建虚拟环境并安装依赖

```bash
cd SiliconRiver

# 创建虚拟环境
python3 -m venv .venv

# 安装依赖（macOS / Linux）
.venv/bin/pip install -r requirements.txt

# Windows 换成：
# .venv\Scripts\pip install -r requirements.txt
```

> **注意**：后面所有命令都用 `.venv/bin/python` 这种**完整路径**，不要直接敲 `python`。否则可能用到系统自带的旧解释器，报缺包错误。

### 3.2 配置 .env

```bash
cp .env.example .env
```

编辑 `.env`，**至少填这两项**：

```ini
# 2.2 里改好的那串
DATABASE_URL=postgresql://postgres.项目ID:密码@aws-0-区域.pooler.supabase.com:5432/postgres?sslmode=require

# 要抓哪些厂商，逗号分隔
PROVIDERS=meta-llama,google,microsoft,openai,01-ai,deepseek-ai,Qwen,mistralai,baichuan-inc,zai-org,tencent
```

**保持默认即可的两项**（重要）：

```ini
VITE_API_BASE=
ENABLE_BRAVE_SEARCH=false
```

- `VITE_API_BASE` **必须留空**（原因见第 0 节）
- `ENABLE_BRAVE_SEARCH=false`：没买 Brave Search 的 Key 就关掉，否则每次抓取都要发一轮无效请求

### 3.3 建表

```bash
.venv/bin/python scripts/init_db.py
```

成功会打印 `PostgreSQL schema ready.`

这一步会在 Supabase 里建 6 张表：`models`、`providers`、`model_tags`、`model_analysis`、`model_arena_info`、`sync_log`。

### 3.4 抓取数据

```bash
# 首次加载：每个厂商 50 条，11 个厂商约 550 条（够展示，约 1-3 分钟）
.venv/bin/python -m src.scraper.fetch_models
```

**想要更多数据**（每个厂商 200 条，约 2200 条）：

```bash
.venv/bin/python -m src.scraper.fetch_models_incr_day
```

数量由 `.env` 的 `HF_DAILY_FETCH_LIMIT` 控制。

> **两个必须知道的点**：
> 1. **必须用 `-m` 模块方式**执行。写成 `python src/scraper/fetch_models.py` 会直接报 `ModuleNotFoundError: No module named 'src'`。
> 2. 抓取脚本**不看命令行参数**，写 `--limit 200` 不会生效，改 `.env` 里的变量才对。
>
> 重复执行是**安全的**：写库用的是 `INSERT ... ON CONFLICT (model_id) DO UPDATE`，也就是"有则更新、无则新增"，不会产生重复数据。

### 3.5 体检：确认数据真的进去了

```bash
.venv/bin/python scripts/check_supabase.py
```

这个脚本会打印：连接是否成功、6 张表各自的行数、最新的 5 条模型记录。**输出会隐藏密码，可以放心截图。**

看到这样就算成功：

```
[连通] 数据库=postgres  用户=postgres.abcdefghijklmnop
------------------------------------------------------------
表名                  状态              行数
------------------------------------------------------------
models                存在               552
providers             存在                11
...
[就绪] 表结构与核心数据都已到位，可以部署前端了。
```

### 3.6 （可选）AI 分析

项目还有个 AI 分析功能（用 DeepSeek 给每个模型生成描述、判定"里程碑"）。**不做也能正常展示**，只是模型详情里没有 AI 生成的简介和里程碑标记。

想做的话，在 `.env` 里填 `DEEPSEEK_API_KEY`，然后：

```bash
.venv/bin/python -m src.scraper.reanalyze_models --older-than-days 0 --no-confirm
```

> 提醒：这是按模型逐个调用大模型，会产生费用和时间。建议先不做，等站点跑起来再补。
> 抓取脚本末尾会自动尝试跑一次 AI 分析，**失败不会影响数据导入**（异常被捕获，只打警告）。

## 4. 第三步：本地跑通再上云

**别跳过这一步。** 本地验证 5 分钟，能省掉在 Vercel 上反复试错的半小时。

## 5. 第四步：部署到 Vercel

### 5.1 把代码推到 GitHub

```bash
cd SiliconRiver
git add -A
git commit -m "整理仓库并适配 Vercel + Supabase 部署"

# 关联远程仓库（换成你自己的地址）
git remote add origin https://github.com/你的用户名/SiliconRiver.git

# 推送
git push -u origin main
```

> **重要提醒**：当前这个工作副本是用压缩包解出来的，**本地 Git 历史与 GitHub 上的原始仓库是两套**。
> 直接 `git push` 会因历史不一致被拒绝。你有两个选择：
> - **推荐**：推到**新分支**，例如 `git push -u origin main:deploy-vercel`，保留原始历史不受影响；
> - 或者确认原仓库内容已备份后，用 `git push -u origin main --force` 覆盖（**有风险，覆盖后原提交记录会丢**）。

### 5.2 在 Vercel 导入项目

1. 打开 <https://vercel.com/new>
2. 找到你的 SiliconRiver 仓库 → **Import**
3. **关键设置**（这一步配错后面全错）：

| 设置项 | 应该填什么 | 为什么 |
|---|---|---|
| **Framework Preset** | **Other** | 前后端是两个 service，由 `vercel.json` 声明，不用预设 |
| **Root Directory** | **保持默认（仓库根目录）** | **千万别设成 `frontend/`**，否则 `vercel.json` 不会被读到 |
| Build Command | 留空 | `vercel.json` 里已声明 |
| Output Directory | 留空 | 同上 |

4. **先别点 Deploy**，先展开 **Environment Variables**（见下一节）。

### 5.3 配置环境变量

在 Environment Variables 里加一条：

| Name | Value | Environments |
|---|---|---|
| `DATABASE_URL` | 2.2 里那串完整连接串 | Production / Preview / Development 全勾 |

> **只需要这一个变量。** API 是纯只读查询服务，不需要 DeepSeek / Brave 的 Key（那些只在**本机抓取时**用）。

### 5.4 部署

点 **Deploy**，等 1–3 分钟。

Vercel 会**同时构建两个 service**：
- `frontend` → 跑 `npm install && npm run build`，产出静态站点
- `backend` → 按 `backend/requirements.txt` 装 Python 依赖，加载 `backend/main.py` 里的 `app`

构建日志里应该能看到两边都成功。

### 5.5 验证线上

部署完成后拿到一个 `https://你的项目.vercel.app` 的地址。

```bash
# 1. 后端健康检查
curl https://你的项目.vercel.app/health

# 2. 后端能读到数据
curl "https://你的项目.vercel.app/api/timeline?preset=all&page_size=3"

# 3. 前端
open https://你的项目.vercel.app
```

三条都通，就算上线成功了。

### 5.6 `vercel.json` 逐行解释

```jsonc
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "services": {
    // 前端 service：root 指向 frontend/，Vercel 自动识别为 Vite 项目
    "frontend": { "root": "frontend/", "framework": "vite" },
    // 后端 service：root 指向 backend/，入口是 main.py 里的 app 变量
    "backend": { "root": "backend/", "framework": "fastapi", "entrypoint": "main:app" }
  },
  "rewrites": [
    // /api/* 的请求转发给后端 service（注意：后端拿到的仍是原始路径 /api/xxx）
    { "source": "/api/(.*)", "destination": { "service": "backend" } },
    { "source": "/health", "destination": { "service": "backend" } },
    // 其余所有请求交给前端
    { "source": "/(.*)", "destination": { "service": "frontend" } }
  ]
}
```

**为什么 `entrypoint` 是 `main:app`**：Vercel 以 `backend/` 为根打包，`main.py` 被当作顶层模块加载，所以写模块名 `main` 而不是 `backend.main`。后端代码里已经做了兼容处理，本地用 `uvicorn backend.main:app` 也照常工作。

### 5.7 自定义域名（可选）

Vercel → 项目 → Settings → Domains → 添加你的域名，按提示在域名服务商处加一条 CNAME。不加也能用 `*.vercel.app` 的地址。

## 6. 第五步：日常运维（每天补新数据）

### 6.1 手动增量

```bash
cd SiliconRiver
bash scripts/daily_sync.sh
```

这个脚本会依次跑 Hugging Face 和 OpenRouter 的增量抓取，日志写到 `logs/daily_sync_日期.log`，并且**一个源失败不阻塞另一个**。

先干跑一次检查环境（不抓数据）：

```bash
bash scripts/daily_sync.sh --dry-run
```

### 6.2 挂成 macOS 定时任务（推荐 launchd）

macOS 上 `launchd` 比 `cron` 可靠：**电脑休眠错过的任务，唤醒后会自动补跑**。

**第一步**，把下面内容存成 `~/Library/LaunchAgents/com.siliconriver.dailysync.plist`（把两处路径换成你的**绝对路径**）：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>
  <string>com.siliconriver.dailysync</string>
  <key>ProgramArguments</key>
  <array>
    <string>/bin/bash</string>
    <string>/Users/你的用户名/路径/SiliconRiver/scripts/daily_sync.sh</string>
  </array>
  <key>WorkingDirectory</key>
  <string>/Users/你的用户名/路径/SiliconRiver</string>
  <key>StartCalendarInterval</key>
  <dict>
    <key>Hour</key><integer>9</integer>
    <key>Minute</key><integer>0</integer>
  </dict>
  <key>StandardOutPath</key>
  <string>/Users/你的用户名/路径/SiliconRiver/logs/launchd.out.log</string>
  <key>StandardErrorPath</key>
  <string>/Users/你的用户名/路径/SiliconRiver/logs/launchd.err.log</string>
</dict>
</plist>
```

**第二步**，加载任务：

```bash
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.siliconriver.dailysync.plist

# 立刻手动触发一次，确认能跑
launchctl kickstart -p gui/$(id -u)/com.siliconriver.dailysync
```

**第三条**：验证

```bash
launchctl list | grep siliconriver          # 应能看到任务
tail -f logs/daily_sync_$(date +%Y%m%d).log # 看运行日志
```

（卸载用 `launchctl bootout gui/$(id -u)/com.siliconriver.dailysync`）

### 6.3 或者用 crontab

```bash
crontab -e
```

加一行（每天 9 点）：

```
0 9 * * * /bin/bash /绝对路径/SiliconRiver/scripts/daily_sync.sh >> /绝对路径/SiliconRiver/logs/cron.log 2>&1
```

> macOS 上 `cron` 有两个已知限制：**休眠期间不会执行**（且不补跑），且新版系统需要在「系统设置 → 隐私与安全性 → 完全磁盘访问权限」里给 `/usr/sbin/cron` 授权。所以优先用 6.2 的 launchd。

### 6.4 让 AI Agent 帮你管（WorkBuddy Automation）

如果不想自己维护 launchd，也可以直接用 WorkBuddy 的自动化任务（对话里说一句"每天 9 点帮我跑增量同步"即可创建）。

需要注意两点：
- 自动化任务需要有**访问本机文件系统的权限**，才能调用 `scripts/daily_sync.sh`
- 任务提示词要写**自包含**，例如："在 /绝对路径/SiliconRiver 下执行 bash scripts/daily_sync.sh，完成后报告本次新增了多少条模型数据"

选择建议：

| 方式 | 适合 | 代价 |
|---|---|---|
| launchd | 只想让它安静地每天跑，不需要汇报 | 需要自己写 plist，出错排查稍麻烦 |
| WorkBuddy Automation | 想顺带拿到一份"今天新增了什么"的中文摘要 | 依赖 WorkBuddy 在运行 |

### 6.5 定时任务体检

```bash
# 看今天有没有跑过
ls -la logs/

# 看最近一次的结果
tail -30 logs/daily_sync_$(date +%Y%m%d).log

# 去数据库确认数据真的在涨
.venv/bin/python scripts/check_supabase.py
```

## 7. 故障排查速查表

### 7.1 本机阶段

| 症状 | 原因 | 解法 |
|---|---|---|
| `ModuleNotFoundError: No module named 'src'` | 抓取脚本被按路径直接执行了 | 用 `-m` 模块方式：`python -m src.scraper.fetch_models` |
| `ModuleNotFoundError: No module named 'psycopg'` | 用错了解释器，没用虚拟环境里的 | 用完整路径 `.venv/bin/python` |
| `No module named 'cgi'` | Python 3.13 移除了 `cgi`，旧版 httpx 依赖它 | 确认 `httpx==0.28.1`（本仓库已更新） |
| `No matching distribution found for psycopg-binary==3.2.1` | 该版本无 Python 3.13 的 wheel | 确认 `psycopg[binary]==3.2.2`（本仓库已更新） |
| `connection refused` / 连接超时 | 用了 Direct connection（仅 IPv6） | 改用 **Session pooler**（5432 端口，IPv4） |
| `password authentication failed` | 用户名少了项目 ID 后缀，或密码含未编码的特殊字符 | 用户名写成 `postgres.项目ID`；密码里的 `@` 等字符做 URL 编码 |
| `RuntimeError: PROVIDERS is not configured` | `.env` 里没填 `PROVIDERS` | 补上，或确认 `.env` 在项目根目录 |
| 抓取很慢或大量 429 | 未配置 Hugging Face Token，触发速率限制 | 在 `.env` 填 `HF_TOKEN` |

### 7.2 Vercel 阶段

| 症状 | 原因 | 解法 |
|---|---|---|
| 部署报 `No framework detected` | Root Directory 被设成了 `frontend/` | 改回**仓库根目录**（留空/默认） |
| 前端 404，但构建成功 | `vercel.json` 没被读到 | 确认它就在**仓库根目录**，且 Root Directory 是根 |
| 前端能打开但数据是空的 | 环境变量没配，或没配到 Production | Vercel 里检查 `DATABASE_URL` 是否勾了 Production |
| `/api/*` 全部 500 | 后端连不上数据库 | 看 Vercel 的 Functions 日志，多半是连接串写错（对照 7.1 的认证/超时两条） |
| `/api/*` 返回 404 | rewrites 没生效 | 确认 `vercel.json` 的 `rewrites` 顺序：`/api/(.*)` 必须在前 |
| 间歇性 `prepared statement ... does not exist` | 事务模式连接池不支持预编译语句 | 代码已通过 `prepare_threshold=None` 处理；若仍有问题，把连接串端口从 6543 换成 5432 |
| 改了环境变量但没生效 | Vercel 需要重新部署才读取新变量 | Deployments → 最新那条 → Redeploy |

### 7.3 通用排查手法

```bash
# 看后端到底报什么错（本地）
.venv/bin/python -m uvicorn backend.main:app --port 8000 --log-level debug

# 看数据库到底有什么
.venv/bin/python scripts/check_supabase.py

# 看前端构建是否真的没问题
cd frontend && npm run build
```
